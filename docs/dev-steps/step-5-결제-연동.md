# AI 사주 서비스 — STEP 5: 결제 연동

## 프로젝트 컨텍스트

AI 사주 MVP. Next.js 풀스택 + Prisma/PostgreSQL, 카카오 로그인 완료.
리포트 생성 파이프라인(PENDING→GENERATING→COMPLETED/FAILED, 1회 생성 후 영구 저장)이 동작 중이며, 현재는 개발용 버튼으로 생성을 트리거하고 있다.

이번 단계: PortOne(V2) + KCP 결제를 붙이고, 결제 확정을 리포트 생성의 유일한 트리거로 만든다.

## 작업 요청

1. 무료 티저 → 결제 퍼널
   - 명식 계산 직후: 사주 8글자 + **에세이 톤 티저 300자 내외**를 무료 공개
   - 티저는 본문과 **동일한 프롬프트·동일한 보이스**로 짧게 별도 생성한다 (`SajuProfile.teaser`에 캐시)
     - 규칙 기반 텍스트로 티저를 만들면 안 된다. 무료로 읽은 문체와 결제 후 받는 에세이의
       문체가 달라지면 "내가 본 거랑 다른 게 왔다"는 반응이 나오고 환불 사유가 된다
     - 잘리는 지점은 **오프닝 & 성향 팩폭(`opening`) 직후** — 가장 궁금한 대목에서 끊는다
   - 티저 아래에 "이어지는 전체 리포트" 잠금 영역 + "전체 리포트 보기" CTA → 로그인 → 결제
     - 리포트가 소제목 없는 한 편의 글이므로, 섹션 단위가 아니라 **본문 흐름이 이어지다 흐려지는**
       형태로 처리한다 (앞 단락 일부를 블러로 겹쳐 보여주면 "계속 읽고 싶은" 압력이 생긴다)
   - LLM 비용 방어
     - 동일 프로필 재방문 시 캐시된 `teaser`를 반환하고 재생성하지 않음
     - IP/세션 기준 rate limit으로 티저 생성 남용 차단
     - 티저는 짧은 출력이므로 본문 대비 호출 비용이 작다는 전제 — 실측해서 단가를 문서화할 것

2. 결제 흐름 (서버 검증 원칙)
   - 주문 생성 API: Order(READY, merchantUid) 생성 후 결제창 호출
   - PortOne 웹훅 엔드포인트: 결제 완료 수신 → PortOne 조회 API로 금액·상태 재검증 → Order를 PAID로 확정 → Report(PENDING) 생성 트리거
   - 프론트 결제 성공 콜백은 UX용으로만 사용, 신뢰하지 않음

3. 멱등성·정합성
   - 웹훅 중복 수신 시에도 리포트는 1건만 생성 (Report의 orderId unique + (sajuProfileId, productCode) unique 제약 활용)
   - 금액 불일치·위변조 시 Order FAILED 처리 + 로그
   - 이미 동일 리포트를 보유한 프로필은 결제 진입 자체를 차단하고 기존 리포트로 안내

4. 결제 실패/취소 UX와 환불 상태(CANCELLED) 처리
   - PortOne 테스트 모드 기준으로 구현하고, 실 KCP 전환 시 바꿀 항목을 문서화

## 검증

- 테스트 결제 → 웹훅 → 리포트 생성까지 E2E
- 같은 웹훅 2번 강제 호출 → 리포트 1건만 존재 확인
- 결제 없이 리포트 생성 API 직접 호출 시 거부되는지 확인
- 티저와 본문을 나란히 읽어보고 **같은 사람이 쓴 글로 읽히는지** 확인 (문체 단절 없음)
- 동일 프로필로 티저 페이지 재진입 → LLM 재호출 없이 캐시가 반환되는지 확인
