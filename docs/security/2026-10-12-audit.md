| S13 | 높음 | DB 접속의 명시적인 인증서 엄격 검증이 준비되지 않았다. Prisma의 `require`/`strict` 설정으로 실제 SELECT 1 연결 검증이 실패했다. | **완료:** 공식 CA 및 PostgreSQL 어댑터로 로컬/운영 TLS·인증서·호스트명 검증 강제. 잘못된 CA/호스트명/비암호화 협상 거부 확인. `pg_stat_ssl`은 풀러 뒤 DB 연결을 나타내므로 이 값 하나로 클라이언트 연결이 평문이라고 단정하지 않았다. |

| S14 | 중간 | 한 탭에서 로그아웃해도 다른 탭의 완료 리포트 및 정적 개인정보 화면이 남을 수 있었다. 공유 브라우저에서 이전 사용자의 내용이 보이는 위험이다. | 실제 카카오 A의 고정 가상 메시지로 재현. 탭 간 폐기 신호·계정 확인 경계·BFCache/창 활성화 검증으로 수정하고 운영에서 완료 리포트/운세함 폐기를 재검증했다. 입력 임시 저장도 계정별 복원/요청 취소로 보완했다. |

새 DB 마이그레이션은 기존 Auth 함수의 권한을 변경하지 않는다. 미래 함수의 기본 PUBLIC EXECUTE 회수는 마이그레이션을 실행한 역할 전체에 적용된다. 다른 역할이 만든 새 테이블/함수는 그 역할의 기본 권한도 별도로 검수해야 한다.

## 통과한 핵심 방어

- Supabase `getUser()` 검증을 사용하며 브라우저가 준 소유자 ID·role·payment status를 신뢰하지 않는다.
- 계정 B는 계정 A의 프로필, 리포트, 생성, 결제 준비, 결제 확인을 사용할 수 없다.
- Supabase의 익명 인증 세션도 정식 로그인 계정으로 인정하지 않는다.
- 익명 및 소유자가 없는 테스트 리포트는 로그인 계정에 자동 귀속되지 않는다.
- 운영 모드에서 미결제 리포트 조회/생성 및 무료 생성 경로가 거부된다. 개발 모드의 결제 생략은 운영 HTTP 서버에 적용되지 않는다.
- 클라이언트 금액·결제 ID·통화·상태 조작, 다른 상점/채널, 결제 시뮬레이션 채널은 구매권을 만들지 못한다.
- 위조·누락·오래된·미래 시각의 웹훅은 DB 변경 전에 거부된다. 알림의 주장보다 공급자 조회 결과를 사용한다.
- 이미 결제/생성된 요청은 같은 주문·리포트를 재사용한다. 동일 정보로 동시 저장해도 중복 구매 대상이 생기지 않는다.
- `x-middleware-subrequest`, 가짜 Authorization/쿠키, 가짜 사용자 헤더, RSC prefetch로 서버 접근 검증을 우회하지 못했다.
- LLM 출력 HTML은 텍스트로 이스케이프된다. 모델에 보내는 해석 payload에는 표시 이름·정확한 생년월일·시각이 들어가지 않는다. Responses 호출은 `store:false`다.
- `.env`, `.git`, 소스/Prisma 파일 직접 URL 및 운영 디자인/테스트 페이지는 공개되지 않는다. 이미지 최적화 API의 임의 외부/루프백 URL도 거부됐다.

### 잔여 의존성과 비밀정보 검사

- `braces <=3.0.3`의 중첩 패턴 서비스 거부 권고가 개발용 ESLint → fast-glob/micromatch 경로에 남아 있다. 이에 따라 npm이 상위 패키지까지 5건으로 집계한다. 웹 요청에서 이 개발 도구를 호출하는 경로는 찾지 못했다. 패치 없는 도구를 없애려고 Next ESLint 설정을 구버전으로 강제 다운그레이드하지 않았다.
- 현재 파일 및 production 클라이언트 번들에서 검사한 비밀 키/DB 접속값 노출은 발견하지 못했다. 개발용 실제 이름도 클라이언트 번들에 없었다.
- Git 기록의 옛 `.env.example`에서 **루프백 DB 접속 비밀번호 형태 문자열 1개**가 감지됐다(두 commit diff에 나타남). 현재 Supabase DB 비밀번호와 다르다. 예시값인지 실제 사용했던 옛 로컬 비밀번호인지 확인이 필요하다. 따라서 `security:secrets`는 이 기록 때문에 exit 1을 유지한다. 실제 비밀번호였고 아직 쓰는 곳이 있으면 해당 비밀번호를 교체해야 한다. 기록은 임의로 재작성하지 않았다.

## 배포 전 남은 작업

1. **완료:** `20261012000000_security_hardening` 실제 DB 적용 및 `security:db`/공개 API/공격 회귀 검증 통과. 기존 사용자·주문·리포트 행은 보존했다.
2. **완료:** 보안 코드·lockfile 및 새 화면을 웹 서버에 배포했다. 운영 도메인의 CSP/X-Frame-Options/nosniff/Referrer-Policy/Permissions-Policy/HSTS를 확인했다(`deployed-headers-after-2026-10-13.json`). 최초 검사 당시 헤더 부재 증거는 `deployed-headers.json`에 보존했다.
3. PortOne의 상점·LIVE 채널·API secret·`PORTONE_WEBHOOK_SECRET`을 배포 환경에 설정한다. 웹훅 URL은 `/api/saju/payments/webhook`, V2 JSON/서명 검증으로 등록한다. Secret 미설정 상태의 새 결제 준비는 거부된다.
4. 결제 공급자 테스트 환경에서 카카오 계정 A/B로 실제 로그인, 자기/가족 프로필, 결제 성공·중단·결과 페이지 재진입·웹훅 재전송·전체/부분 취소·계정 간 URL 이동을 확인한다. TEST 결제 채널은 운영 모드에서 의도적으로 거부되므로 테스트용 개발/격리 환경에서 수행한다. 운영 LIVE 결제는 사용자 직접 실행 단계다.
5. Supabase Auth Redirect allowlist·토큰 수명·로그 접근 권한, Vercel 환경변수/배포 권한·WAF·로그 보존·백업/복구 권한은 관리 콘솔에서 확인한다. 이번 코드 검사로 해당 설정을 확인했다고 주장하지 않는다.
6. 만료된 `SecurityRateLimit` 행 정리를 운영 작업으로 설정한다. TTL 인덱스는 추가했지만 정기 삭제 작업은 만들지 않았다.
7. **완료:** 공식 Supabase root CA를 포함하고 공통 PostgreSQL 어댑터에서 엄격한 TLS·인증서·호스트명 검증을 강제했다. 로컬/운영 사전검증 및 10개 TLS 회귀 검사 통과 후 재배포했다. 비밀번호/키 및 OS 전체 신뢰 저장소는 변경하지 않았다. Mac migration CLI의 별도 제한은 위 완료 항목 및 인증서 README에 기록했다.

현재 CSP는 `base-uri`, `object-src`, `frame-ancestors`를 막는 최소 정책이다. script-src nonce 기반의 완전한 정책을 적용했다고 주장하지 않는다. 실제 결제 SDK/PG iframe까지 검증한 뒤 추가할 수 있다.
