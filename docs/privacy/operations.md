# 개인정보·환불 운영 절차

검토일: 2026-10-28 · 정책 버전: 2026-10-28.2 · 담당: 찌야 대표 최혜지

## 출시 상태

- 사이트 `/privacy`, `/refund`, `/support`와 실제 서버 동작을 연결했다.
- 정책 시행일은 아직 미지정, 신규 실결제 차단 유지. 계약상 국외 이전 항목, PG 승인·실결제/취소 검증, 백업/복원 검증을 완료한 것으로 보지 않는다.
- 운세 조회 대상은 **만 14세 이상만** 허용한다(2026-10-28 사용자 결정). 본인·가족·친구·연인·기타 모두 같으며 보호자 입력 예외는 없다. 법정대리인 동의 절차를 갖추기 전에는 아동 운세를 추가하지 않는다.
- 실제 고객 삭제·카드 취소를 이번 개발 검증에서 실행하지 않는다. 아래 실행 명령은 실제 요청이 있고 대상이 확인된 경우에만 사용한다.
- 운영자는 영업일마다 `privacy:requests`와 고객센터 이메일·전화 요청을 확인한다. 접수 시각부터 법정 기한을 관리한다. 자동 이메일·카카오 알림 발송은 아직 없다.

## 1. 고객 접수 / 본인 확인

고객은 `/support`에 로그인하여 환불 또는 전체 계정 탈퇴를 접수한다. 서버가 세션에서 요청자를 정하며 브라우저가 보낸 `userId`는 받지 않는다. 출처 검사·크기 제한·계정별 일일 6회 제한을 적용한다. 주문번호를 입력했다면 소유권도 확인한다. 네트워크 재시도는 같은 요청 번호를 반환한다.

고객센터 이메일·전화로도 권리 행사 가능하다. 접수번호와 회신 연락처, 신청 사유를 필요한 범위에서 받는다. 이메일 주소가 같다는 이유만으로 계정 소유자로 단정하지 않는다. 로그인 가능한 고객은 온라인 접수번호와 연결하여 확인한다. 로그인 불가능, 대리인, 타인이 입력한 정보의 당사자는 권한·대상 확인을 별도로 진행한다. 신분증 전체·주민등록번호·카드번호·비밀번호를 채팅/이메일로 받지 않는다. 과도한 증빙 대신 필요한 항목만 가리고 확인한다.

```sh
# 읽기 전용. 운영 요청을 오래된 순으로 최대 100개 (100개라면 추가 요청 점검 필요)
npm run privacy:requests
# 결제 테스트 네임스페이스
npm run privacy:requests -- --test
```

온라인 요청은 담당자가 확인할 수 있는 DB에 저장된다. 접수 버튼만으로 돈을 취소하거나 정보를 지우지 않는다. 별도의 메일 발송도 하지 않는다. 담당자는 최초 접수 시각, 법정 기한, 확인 내용, 판단 근거와 고객 통지를 보안이 적용된 상담 기록에 남긴다. 공개 저장소·이슈에는 고객 정보나 원문 문의를 올리지 않는다.

개인정보 열람 및 정정·삭제·처리정지는 해당 법정 요건과 10일 통지 기준을 확인하여 처리한다. 정당한 연기·제한 사유가 있으면 근거와 이의 제기 방법을 기한 내 안내하며, 일반 문의의 내부 처리 순서로 법정 기한을 미루지 않는다. [법제처 권리 요구 처리 안내](https://easylaw.go.kr/CSP/CnpClsMain.laf?ccfNo=2&cciNo=2&cnpClsNo=2&csmSeq=1257&popMenu=ov)

## 2. 환불 절차

1. 접수 시각을 먼저 기록한다. 주문번호/결제일/금액으로 계정의 주문과 PortOne 실제 거래를 대조한다. 이메일에 온 다른 사람의 주문번호만으로 취소하지 않는다.
2. 리포트 생성 상태, 실제 제공 여부, 하자·중복·계약 불이행을 확인한다. `completedAt`는 생성, `firstDeliveredAt`는 본문 응답 준비, `firstOpenedAt`는 보이는 브라우저의 렌더 확인이다. 어느 한 기록도 실제 읽기나 모든 환불 제한을 입증하지 않는다.
3. 제공 전 법정 기간 내 철회, 생성 실패·미제공, 중복 과금, 하자/계약 불일치를 구분한다. ‘사주 상품이라 환불 불가’, ‘생성 버튼 눌렀으니 불가’, ‘운세가 마음에 들지 않으니 항상 전액 환불’처럼 일괄 판단하지 않는다.
4. 디지털콘텐츠 또는 미제공 재화의 적법한 철회는 철회한 날부터 3영업일 이내 환급. 내부 승인일로 기산일을 미루지 않는다. 카드 청구 정지·취소 요청은 지체 없이 진행한다. 카드사 반영 지연과 판매자의 환급 의무를 구분한다.
5. 대상·금액을 확정하고 권한 있는 운영자가 PortOne 콘솔에서 원 결제 취소를 실행한다. 이 저장소의 지원 요청 명령은 결제 취소 API를 호출하지 않는다. 취소 요청 재시도 전 실제 상태를 먼저 확인한다.
6. PortOne 실제 취소 상태, 서명 검증 웹훅 처리, 로컬 주문 `CANCELLED`, 재조회·재생성 차단을 확인한다. 웹훅 실패 시 정상 재전송/조회로 복구하며 서명·상점 검사를 끄지 않는다. 부분 취소도 현재 구현은 전체 운세 권한을 차단하므로 부분 환불 전 이용 조건을 별도로 확정한다.
7. 고객에게 결과·금액·수단·처리 시각과 이의 제기 방법을 알린다. 거절이면 구체적 근거를 기록하고 알린다. 탈퇴한 고객도 권리가 유지된다.
8. 완료된 문의를 닫는다. 결과 코드만 적는 것으로 판단 근거/회신 기록을 대체하지 않는다.

```sh
# 실제 환불 완료와 고객 통지를 확인한 뒤에만 실행
npm run privacy:requests -- --close support_REQUEST_ID --outcome REFUNDED --customer-notified
# 다른 결과: DECLINED_WITH_REASON / RESOLVED / WITHDRAWN
```

탈퇴 후 환불은 `legalRecords/{orderId}`로 대조하고 PortOne에서 처리한다. 보관 레코드에 취소/환급 시각·금액을 추가하고, 거래 보관 종료일을 해당 사건 이후 5년으로 갱신한다. 법적 보존 중(`legalHold=true`)이면 `purgeAt=null`을 유지한다. 자동 복원이나 새 리포트 발행을 하지 않는다.

## 3. 전체 계정 삭제

### 실행 전

- **로그인한 당사자의 ACCOUNT_DELETE 요청**이 필요하다. CLI는 해당 접수번호·계정·가입 시점·명시적 확인을 검사한다. 이메일로만 요청한 계정은 임의로 온라인 접수 행을 위조하지 않는다. 접근 회복 또는 별도 본인 확인 후 승인된 수동 절차로 처리하고 감사 기록을 남긴다.
- 해당 계정의 모든 사람(나·가족·친구·연인)의 프로필/리포트가 삭제되는 범위를 알린다. 개별 타인 정보 정정·삭제 요청은 전체 탈퇴 명령으로 처리하지 않는다.
- 미결제/결제 진행 중 주문까지 PortOne 실제 상태를 조회한다. 늦게 승인될 수 있는 결제창을 종료하고 미결제 확정 또는 취소/환불을 처리한 뒤 진행한다. `--payments-reviewed`는 실제 확인을 마친 운영자의 확인이며 자동 PG 검사라는 의미가 아니다.
- 분쟁·소송 등 별도 보존 필요 시 필요한 증빙만 보존하며 해당 주문 `legalHold=true`와 근거·해제 검토일을 기록한다. 원국·생년월일·전체 리포트를 일괄 보존하지 않는다.
- dry run의 프로젝트, 두 네임스페이스, 대상 UID, 건수를 확인한다. 실고객 자료를 테스트로 삭제하지 않는다.

```sh
# 기본은 조회만. 이름·생년월일·운세 본문은 출력하지 않는다.
npm run privacy:account -- --uid kakao_USER_ID
# 실제 접수·본인·결제 확인을 마친 경우에만 실행한다.
npm run privacy:account -- --uid kakao_USER_ID --apply --confirm-uid kakao_USER_ID --case-id support_REQUEST_ID --identity-verified --payments-reviewed
```

### 실행 동작

1. 운영/결제 테스트 두 네임스페이스의 사용자를 하나의 DB 트랜잭션으로 잠근다. 같은 요청 번호 외에는 잠금을 넘겨받지 못한다.
2. Firebase Auth 계정을 사용 중지하고 갱신 토큰·서버 세션을 폐기한다. 신규 프로필/주문/생성/본문 저장도 트랜잭션 안에서 삭제 잠금을 확인한다.
3. 주문별 거래 식별자·금액·상태·동의 문구/버전·제공/열람 시각만 `legalRecords`에 원자적으로 옮긴다. 이름·출생 정보·명식·리포트 본문·프로필 ID는 복사하지 않는다. 영구 보관이 아닌 `purgeAt`을 설정한다.
4. `profiles`, `reports`, `checkoutConsents`, 운영 주문 및 Firebase Auth/사용자 문서를 삭제한다. 법정보존 `legalRecords`와 처리 증빙만 남긴다. 요청 제한 해시는 짧은 만료 주기로 삭제된다.
5. 요청·삭제 작업 기록을 완료하고 3년 뒤 만료를 지정한다. 실수로 완료된 접수번호를 재실행해도 재가입 계정을 삭제하지 않는다.
6. 조회 계획을 다시 실행해 계정/프로필/리포트/주문/동의/세션 0건을 확인한다. 법정보존 필드, 이전 쿠키 접근 불가, 새 로그인 시 삭제한 자료가 되살아나지 않는지 확인한다.

중간 실패는 **완료가 아니다**. 계정은 차단 상태로 유지된다. 데이터나 잠금 문서를 손으로 초기화하지 말고 원인을 해결한 후 같은 UID·접수번호로 재실행한다. 완료 사실을 확인하기 전에 고객에게 삭제 완료를 알리지 않는다. 재가입은 새로운 데이터 구분값을 사용하므로 예전 PG 결제번호나 운세 권한을 재사용하지 않는다.

## 4. 보존표와 실제 자동 삭제

| 자료 | 서비스 이용 중 | 삭제·분리 후 | 실제 방식 |
|---|---|---|---|
| 사용자/프로필/명식/운세 본문 | 서비스 제공에 필요한 기간 | 본인 확인한 삭제 처리 시 제거 | 운영자 승인 삭제 도구 |
| 계약·결제·공급 증빙 | 거래 이행/운세 재조회에 사용 | 관련 거래/공급/철회 사건 기준 5년 | 최소 필드 별도 `legalRecords`, `purgeAt` TTL |
| 분리된 미결제 임시 주문 | 결제 처리 상태 확인 필요 | 마지막 관련 기록일 기준 30일 | `legalRecords` TTL |
| 온라인 문의·삭제 처리 증빙 | 진행 중 필요한 기간 | 완료 후 3년 | `serviceRequests`, `privacyJobs` TTL |
| 표시·광고 | 정책/상품 예시 버전 증빙 | 6개월 이상 법정 보존 | Git의 공개 상품/정책 이력, 개인 리포트 제외 |
| OAuth | 10분 유효 | 만료 뒤 자동 제거 | `expiresAt` TTL |
| 세션 | 최대 14일 유효, 로그아웃 즉시 폐기 | 만료 뒤 자동 제거 | `expiresAt` TTL |
| 요청 제한 | 해당 제한 구간(분~일) | 만료 뒤 자동 제거 | `resetAt` TTL |
| Cloud Logging 일반 로그 | 30일 | 제공자 만료 삭제 | `_Default` 실제 설정 확인 |
| 필수 관리 감사 로그 | 400일 | 제공자 만료 삭제 | `_Required` 잠긴 Google 설정 |

TTL은 보통 만료 후 24시간 이내이나 지연될 수 있다. 권한은 만료 시각을 별도로 검사한다. TTL을 활성 서비스의 사용자·프로필·주문·리포트 컬렉션 전체에 걸지 않는다. 보존 중 분쟁은 `purgeAt=null`로 제외하며 담당자가 근거/해제 시점을 주기적으로 검토한다. 진행 중 고객 요청을 TTL로 조용히 버리지 않는다.

문의 이메일·전화 메모 등 DB 밖 사본도 같은 기준으로 정리한다. 일반 Gmail 메일함에는 사건 단위 자동 삭제를 구성하지 않았으므로 운영자가 완료 사건의 보관 만료 목록을 관리하고 원문·첨부·휴지통을 정리한다. 식별정보가 든 파일을 Git·공개 드라이브에 넣지 않는다.

## 5. 인프라 및 제공자 확인

2026-10-28 읽기 전용 확인: DB `asia-northeast3`(서울), App Hosting `asia-east1`(대만), TTL 정책 기존 0개, 자동 백업 없음, PITR/삭제 방지 꺼짐. 이번 변경에서 TTL 구성은 `firestore.indexes.json`으로 관리한다. 배포/활성화 결과는 검증 기록에 따로 남긴다.

- Firestore 자동 백업/복원은 별도 출시 작업이다. 보관 기간(예: 일일 백업 7일)을 결정하고 비용 확인·실제 복원 검증 후 공개 방침에 반영한다. 아직 활성화됐다고 안내하지 않는다.
- 백업 도입 후에는 삭제 작업 목록을 복원 대상보다 최신 상태로 확보하고, 복원 DB를 서비스에 연결하기 전에 삭제 요청을 재반영한다. 복원으로 이미 삭제한 운세가 재등장해서는 안 된다.
- Firebase Auth 자체 운영/백업 삭제 최대 180일은 다봄의 Firestore 백업 주기와 별개다.
- OpenAI Responses 요청은 `store:false`; 실제 프로젝트의 데이터 공유 opt-in·지역 설정·계약 법인·재위탁 국가를 추가 확인한다. 이 옵션만으로 ZDR나 미국 단일 처리를 주장하지 않는다.
- 공개 고객센터 이메일 제공자(Gmail)도 국외 처리 검토에 포함한다. 고객센터 문의 내용을 서비스 DB 처리 범위에만 한정해 고지하지 않는다.
